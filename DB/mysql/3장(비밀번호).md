# 3장 - 계정설정/비밀번호

---

## **3. 내장 계정(Built-in Account)**

MySQL에는 사용자가 직접 만든 것이 아니라 서버 내부 동작을 위해 미리 존재하는 계정들이 있다.

대표적으로 다음과 같은 계정이 있다.

- 'mysql.sys'@'localhost'
- 'mysql.session'@'localhost'
- 'mysql.infoschema'@'localhost'

### **3-1. 각각의 역할**

### **'mysql.sys'@'localhost'**

sys 스키마 객체들의 DEFINER로 사용된다.

즉, sys 스키마 내부 뷰나 객체가 어떤 권한 기준으로 실행될지를 정의하는 데 쓰인다.

### **'mysql.session'@'localhost'**

MySQL 플러그인이나 내부 서버 기능이 서버에 접근할 때 사용하는 계정이다.

### **'mysql.infoschema'@'localhost'**

information_schema 관련 뷰들의 DEFINER로 사용된다.

### **3-2. 실무 관점 정리**

이 계정들은 보통 **직접 로그인해서 쓰는 계정이 아니다.**

내부 동작용이므로 존재를 아는 정도면 충분하고, 특별한 이유 없이 수정하거나 삭제하면 안 된다.

## **5. CREATE USER 명령 쉽게 이해하기**

예시:

```
CREATE USER 'user'@'%'
  IDENTIFIED WITH mysql_native_password BY '1q2w3e'
  REQUIRE NONE
  PASSWORD EXPIRE INTERVAL 30 DAY
  ACCOUNT UNLOCK
  PASSWORD HISTORY DEFAULT
  PASSWORD REUSE INTERVAL DEFAULT
  PASSWORD REQUIRE CURRENT DEFAULT;
```

---

### **5-1.**

### **'user'@'%'**

이 사용자는 이름이 user이고, 모든 호스트(%)에서 접속 가능하다는 뜻이다.

즉, 네트워크 관점에서 꽤 넓게 열려 있는 계정이다.

실무에서는 편해서 자주 쓰지만, 운영 환경에서는 너무 넓은 범위일 수 있으므로 주의가 필요하다.

---

### **5-2.**

### **IDENTIFIED WITH ... BY ...**

이 부분은 **어떤 인증 방식으로 비밀번호를 검증할 것인지**를 설정한다.

```
IDENTIFIED WITH mysql_native_password BY '1q2w3e'
```

의 뜻은,

- 인증 플러그인: mysql_native_password
- 실제 비밀번호: 1q2w3e

라는 의미다.

---

### **5-3.**

### **REQUIRE NONE**

SSL/TLS 같은 보안 연결을 강제하지 않겠다는 뜻이다.

즉,

- 암호화 연결 필수 아님
- 일반 연결도 허용

이라는 의미다.

보안 요구사항이 큰 환경에서는 REQUIRE SSL 등의 설정을 고려할 수 있다.

---

### **5-4.**

### **PASSWORD EXPIRE INTERVAL 30 DAY**

비밀번호를 30일마다 만료되게 한다는 뜻이다.

즉,

- 계정을 계속 쓸 수는 있지만
- 30일이 지나면 비밀번호 변경을 요구할 수 있음

이라고 이해하면 된다.

---

### **5-5.**

### **ACCOUNT UNLOCK**

계정을 잠금 해제된 상태로 생성한다는 의미다.

반대로 잠긴 계정이면 인증이 되더라도 사용할 수 없다.

---

### **5-6.**

### **PASSWORD HISTORY DEFAULT**

예전에 사용했던 비밀번호를 곧바로 다시 쓰지 못하도록 하는 정책과 관련이 있다.

여기서는 기본 정책을 따르겠다는 의미다.

---

### **5-7.**

### **PASSWORD REUSE INTERVAL DEFAULT**

이전에 사용한 비밀번호를 얼마 동안 재사용하지 못하게 할지에 대한 정책이다.

이 역시 기본값을 사용한다는 뜻이다.

---

### **5-8.**

### **PASSWORD REQUIRE CURRENT DEFAULT**

비밀번호를 바꿀 때 현재 비밀번호를 요구할지 여부에 대한 정책이다.

즉,

- 비밀번호 변경 시 본인 확인을 더 엄격히 할 것인가
- 아니면 관리자가 강제로 바꾸는 흐름을 허용할 것인가

와 연결된다.

---

## **6. 인증 플러그인 변화:**

## **mysql_native_password**

## **→ caching_sha2_password**

이 부분은 “왜 갑자기 MySQL 8.0에서 접속이 안 되지?”와 관련되어 매우 자주 등장한다.

### **6-1. MySQL 5.7 기본 인증 방식**

MySQL 5.7에서는 기본적으로 mysql_native_password가 널리 사용되었다.

### **6-2. MySQL 8.0 기본 인증 방식**

MySQL 8.0에서는 기본 인증 플러그인이 caching_sha2_password로 변경되었다.

즉, 특별히 지정하지 않으면 8.0에서는 더 강화된 인증 방식을 사용하는 것이 기본이다.

---

### **6-3. 왜 바뀌었을까?**

보안 강화를 위해서다.

기존 방식보다 더 안전한 해시/인증 구조를 제공하기 때문이다.

---

### **6-4. 그런데 왜 문제가 생길까?**

문제는 일부 오래된 클라이언트, 드라이버, 라이브러리가 caching_sha2_password를 완전히 지원하지 못할 수 있다는 점이다.

그 결과,

- 서버는 문제없는데
- 애플리케이션에서 접속 오류 발생
- 드라이버 호환성 문제 발생

같은 상황이 생길 수 있다.

---

### **6-5. 해결 방법**

호환성 문제가 있다면 계정을 기존 방식으로 바꿔줄 수 있다.

```
ALTER USER 'username'@'host'
IDENTIFIED WITH mysql_native_password BY 'password';
```

이 명령은 해당 계정의 인증 플러그인을 mysql_native_password로 바꾸고 비밀번호를 다시 설정하는 의미다.

### **6-6. 실무적으로 어떻게 이해하면 좋을까?**

- **기본 원칙**: 가능하면 8.0 기본 방식(caching_sha2_password) 사용
- **예외 상황**: 구형 드라이버/도구 때문에 접속이 안 되면 mysql_native_password 고려

즉, 더 좋은 보안 방식이 기본이 되었지만,

호환성 문제가 있으면 잠시 이전 방식을 선택할 수 있다고 이해하면 된다.

## **7. 비밀번호 정책과**

## **validate_password**

MySQL은 단순히 비밀번호를 저장하는 것뿐 아니라,

**비밀번호가 너무 약하지 않은지 검사하는 정책**도 제공한다.

이때 대표적으로 쓰이는 것이 validate_password 기능이다.

문맥에 따라 플러그인/컴포넌트 형태로 설명되기도 하지만,

> 사용자가 비밀번호를 설정할 때, 길이나 복잡도 기준을 만족하는지 검사해 준다.
> 

---

### **7-1. 비밀번호 정책 수준**

비밀번호 정책은 보통 다음 세 단계로 이해하면 된다.

### **LOW**

가장 낮은 수준이다.

주로 **최소 길이** 정도만 검사한다.

즉,

- 너무 짧은 비밀번호는 막지만
- 숫자/대문자/특수문자 조합까지는 강하게 요구하지 않을 수 있다.

### **MEDIUM (기본)**

가장 많이 언급되는 기본 수준이다.

보통 다음을 함께 본다.

- 길이
- 숫자 포함 여부
- 영문 대소문자 포함 여부
- 특수문자 포함 여부

즉, 실무에서 일반적으로 기대하는 “적당한 복잡도”를 요구하는 수준이다.

### **HIGH**

더 엄격한 수준이다.

기본 복잡도에 더해 **금칙어(dictionary)** 검사까지 포함할 수 있다.

예를 들어,

- 회사명
- 계정명
- 너무 흔한 문자열
- 금지 단어 목록

등이 들어간 비밀번호를 막을 수 있다.

---

### **7-2. 왜 dictionary가 중요할까?**

MySQL은 기본적으로 단순 연속 문자열인

- 1234
- qwerty
- abcd

같은 패턴을 자동으로 모두 막아주지는 않을 수 있다.

그래서 보안이 중요한 환경이라면 금칙어 사전을 잘 관리하는 것이 중요하다.

즉, **복잡도 검사만으로는 충분하지 않을 수 있다**는 뜻이다.

---

## **8. 이중 비밀번호(Dual Password)**

이 부분은 처음 보면 “2차 비밀번호?”처럼 느껴질 수 있는데, 그 개념과는 다르다.

### **8-1. 이중 비밀번호의 의미**

하나의 계정이 **동시에 두 개의 비밀번호를 가질 수 있는 기능**이다.

즉,

- 기존 비밀번호
- 새 비밀번호

를 일정 기간 함께 인정해 줄 수 있다.

---

### **8-2. 왜 이런 기능이 생겼을까?**

운영 환경에서는 DB 비밀번호를 바꾸는 일이 생각보다 어렵다.

왜냐하면 DB를 쓰는 대상이 한두 개가 아닐 수 있기 때문이다.

예를 들어,

- 웹 서버
- 배치 서버
- 백오피스
- CI/CD 파이프라인
- 운영 스크립트

등 여러 곳에 같은 DB 비밀번호가 들어 있을 수 있다.

이 상황에서 비밀번호를 그냥 바꿔 버리면,

아직 새 비밀번호로 바꾸지 못한 서비스들은 즉시 DB 접속에 실패한다.

즉,

**운영 장애가 발생할 수 있다.**

---

### **8-3. 이중 비밀번호가 해결하는 문제**

이중 비밀번호는 비밀번호 교체를 “한 번에 끊어서”가 아니라,

**점진적으로 바꾸도록 도와준다.**

흐름은 보통 이렇다.

1. 새 비밀번호를 추가한다.
2. 기존 비밀번호도 계속 유효하게 둔다.
3. 애플리케이션, 시크릿 관리 툴, 배치 설정 등을 새 비밀번호로 바꾼다.
4. 모두 전환이 끝나면 예전 비밀번호를 제거한다.

즉, 서비스 중단 없이 비밀번호를 회전(rotation)할 수 있다.

---

### **8-4. 실무 예시 관점**

예를 들어 root@localhost 또는 애플리케이션 계정의 비밀번호를 바꾸고 싶다고 하자.

그냥 다음처럼 바꾸면:

```
ALTER USER 'root'@'localhost' IDENTIFIED BY 'new_password';
```

즉시 새 비밀번호만 유효해진다.

그러면 기존 비밀번호를 쓰던 프로그램들은 모두 실패한다.

반면 이중 비밀번호 개념을 쓰면,

기존 비밀번호와 새 비밀번호를 함께 인정하는 기간을 둘 수 있다.

따라서 운영 중 서비스에 더 안전하다.

---

### **8-5. 한 줄 정리**

> 이중 비밀번호는 보안을 위한 2차 인증 기능이 아니라, 운영 중 비밀번호를 안전하게 교체하기 위한 기능이다.
>

## **9. 권한 관리와 GRANT**

계정을 만들었다고 해서 바로 모든 작업을 할 수 있는 것은 아니다.

무엇을 할 수 있는지는 **권한(privilege)** 으로 제어한다.

대표적으로 다음과 같은 권한이 있다.

- SELECT : 조회
- INSERT : 삽입
- UPDATE : 수정
- DELETE : 삭제
- CREATE : 생성
- DROP : 삭제(객체 제거)

예를 들어:

```
GRANT SELECT, INSERT ON database_name.* TO 'username'@'host';
```

의 뜻은,

- username@host 계정에게
- database_name 데이터베이스의 모든 테이블에 대해
- 조회와 삽입 권한을 주겠다는 의미다.

---

## **10. MySQL 8.0에서 GRANT 관련 변화**

### **10-1. CREATE USER와 GRANT의 분리**

앞에서 설명했듯이 8.0에서는 계정 생성과 권한 부여를 분리해서 수행한다.

즉,

1. CREATE USER
2. GRANT

순서로 이해하는 것이 맞다.

---

### **10-2. WITH GRANT OPTION의 의미**

WITH GRANT OPTION은 단순히 권한을 받는 것에서 끝나지 않고,

**자기가 가진 권한을 다른 사용자에게도 줄 수 있는 능력**이다.

하지만 8.0에서는 이 부분이 더 엄격하게 다뤄진다.

즉,

- 내가 실제로 받지 않은 권한을 남에게 줄 수는 없고
- 권한 전파를 더 조심스럽게 제어한다.

이것은 보안 측면에서 매우 중요하다.

잘못하면 일반 사용자가 관리자처럼 권한을 퍼뜨릴 수 있기 때문이다.

---

## **11. SUPER 권한의 분할**

이 부분도 8.0의 핵심 변화 중 하나다.

### **11-1. 예전의 SUPER 권한**

MySQL 5.7 시절에는 SUPER 권한 하나가 너무 많은 일을 할 수 있었다.

즉,

- 서버 설정 변경
- 복제 관련 제어
- 로그 관련 작업
- 각종 운영 작업

등이 한 권한 안에 크게 묶여 있었다.

문제는 이것이 지나치게 강력하다는 점이다.

운영상 특정 작업 하나만 필요해도 SUPER를 주면 너무 많은 권한을 함께 주게 된다.

---

### **11-2. MySQL 8.0의 변화**

8.0에서는 SUPER 권한을 여러 개의 세부 권한으로 나누었다.

대표 예시는 다음과 같다.

- BINLOG ADMIN : 바이너리 로그 관련 작업
- REPLICATION SLAVE ADMIN : 복제 서버 관리
- SYSTEM_VARIABLES_ADMIN : 글로벌 시스템 변수 변경

즉, 필요한 작업에 필요한 권한만 따로 부여할 수 있게 되었다.

---

### **11-3. 왜 좋은가?**

이 변화의 핵심은 **최소 권한 원칙(Principle of Least Privilege)** 이다.

즉,

- 꼭 필요한 권한만 주고
- 불필요한 관리자 권한은 주지 않는 방향

으로 보안 수준을 높인 것이다.

예를 들어 바이너리 로그 관리만 필요한 사용자에게 굳이 전체 서버 관리 권한을 줄 필요가 없다.

---

## **12. 전체 흐름으로 다시 이해하기**

지금까지 내용을 흐름으로 정리하면 다음과 같다.

### **12-1. 사용자 식별**

MySQL은 사용자를 아이디만이 아니라 아이디 + 접속 위치(host)로 구분한다.

### **12-2. 계정 생성**

MySQL 8.0에서는 CREATE USER로 먼저 계정을 만든다.

### **12-3. 인증 방식**

그 계정이 어떤 인증 플러그인으로 비밀번호를 검증할지 정한다.

기본은 caching_sha2_password다.

### **12-4. 비밀번호 정책**

비밀번호는 길이/복잡도/금칙어 정책을 적용할 수 있다.

### **12-5. 권한 부여**

계정을 만든 뒤 GRANT로 어떤 작업을 허용할지 정한다.

### **12-6. 운영 중 변경**

비밀번호를 바꾸거나 권한을 조정할 때는 운영 장애가 나지 않도록 신중하게 처리해야 하며, 이중 비밀번호 같은 기능이 도움이 된다.
