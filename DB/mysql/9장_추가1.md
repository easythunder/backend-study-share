# **1) 옵티마이저가 하는 일 & EXPLAIN 의미**

## **옵티마이저(Optimizer)란?**

- MySQL은 SQL을 받으면, 그 SQL을 “어떤 순서로”, “어떤 인덱스를 쓰고”, “어떤 조인 방식으로” 실행할지 결정해야 함.
- 같은 SQL이라도 실행 방법은 여러 개가 가능해. 예를 들면:
    - 인덱스를 타고 찾을지 vs 테이블을 풀스캔할지
    - A 테이블부터 조인할지 vs B 테이블부터 조인할지
    - 정렬을 파일 정렬(filesort)로 할지 vs 인덱스 정렬을 그대로 이용할지
- **옵티마이저는 이런 후보 실행 방법들 중에서 “비용(cost)”이 가장 낮을 것 같은 실행 계획을 선택**해.
    - 여기서 cost는 보통 “디스크 I/O, 읽어야 하는 레코드 수, 중간 결과 크기, 정렬/임시테이블 비용” 같은 것들이 합쳐진 개념임.

## **EXPLAIN은 왜 보나?**

- EXPLAIN은 “이 SQL을 MySQL이 어떤 방식으로 실행할지”를 **실행 계획 형태로 보여주는 도구**야.
- 실무적으로는 EXPLAIN을 통해 다음을 확인하는 게 핵심:
    - 지금 인덱스를 제대로 타고 있나?
    - 조인 순서가 이상하진 않나?
    - Using temporary, Using filesort 같은 “비싼 작업”이 붙어 있나?
    - 실제로 읽는 row 수 추정치가 과도하게 크지 않나?

## **포인트!!**

- SQL 튜닝 = “쿼리 자체만 고치는 것”도 있지만, 실제로는 **옵티마이저가 좋은 선택을 하도록 인덱스/쿼리 형태를 맞춰주는 작업**이 큰 비중을 차지함.
- 그래서 EXPLAIN은 튜닝의 출발점이자 디버깅 도구 역할을 함.

# **2) 스트리밍 처리 vs 버퍼링 처리**

MySQL이 결과를 사용자에게 반환하는 방식은 크게 두 흐름으로 생각할 수 있어.

## **스트리밍(Streaming) 방식**

- 조건에 맞는 레코드를 찾는 즉시, 결과를 **바로바로 클라이언트(또는 다음 처리 단계)로 전달**하는 방식.
- 특징:
    - **첫 결과를 빨리 받는다** (체감 응답성이 좋음)
    - 중간 결과를 크게 모아두는 과정이 적어서 메모리 부담이 상대적으로 낮을 수 있음
- LIMIT과 궁합이 좋아.
    - 스트리밍은 찾는 즉시 보내는구조 라서, LIMIT 10 같은 게 있으면 10개 채우면 바로 멈출 수 있음.
    - 즉, **전체 처리량 자체가 줄어드는 효과**가 생기기 쉬움.

### **스트리밍으로 끝날 가능성이 큰 경우**

- 단순 조건 조회 (WHERE ...) + 적절한 인덱스
- 정렬/그룹핑이 없거나, 인덱스 정렬로 대체 가능한 경우

## **버퍼링(Buffering) 방식**

- 결과를 바로 보내지 못하고, 중간에 **한 번 모아서 처리한 뒤** 최종 결과를 반환하는 방식.
- 대표적으로 아래 작업들이 들어가면 버퍼링이 필요해지는 경우가 많아:
    - ORDER BY (정렬해야 함)
    - GROUP BY (그룹핑/집계를 위해 모아야 함)
    - DISTINCT (중복 제거를 위해 모아야 함)
- 특징:
    - **첫 결과가 늦게 나온다** (처리가 끝나야 내보낼 수 있음)
    - 정렬/그룹핑 중간 과정에서 **임시테이블**이나 추가 메모리/디스크 작업이 붙을 수 있음

## **LIMIT은 항상 성능을 올려줄까?**

- 스트리밍에서는 LIMIT이 “빨리 끝내는” 효과가 커서 잘 먹히는 편.
- 하지만 버퍼링 작업(특히 정렬/그룹핑)이 있으면 상황이 달라질 수 있어.
    - 예: ORDER BY로 전체를 정렬한 다음 상위 10개를 뽑는 구조라면, **정렬 자체는 이미 많은 데이터를 다 만져야** 해서 LIMIT이 생각만큼 시간을 줄이지 못할 수 있음.
- 결론적으로:
    - LIMIT이 있다고 무조건 빠르진 않고,
    - “스트리밍이 가능한 구조인지 / 버퍼링이 강제되는 구조인지”를 같이 봐야 함.

# **3) 정렬 상태 변수(서버가 정렬을 얼마나 했는지 보는 힌트)**

정렬이 많아지면 성능이 흔들리는 경우가 많아서, 서버 내부적으로 정렬이 얼마나 발생했는지 **상태 변수**로 간접 체크할 수 있어.

## **주요 변수 의미**

- Sort_merge_passes
    - 정렬 과정에서 “한 번에 다 못 정렬해서” 중간 결과를 여러 덩어리로 만든 뒤,
    - 그걸 **다시 합치는(merge) 작업**이 몇 번 발생했는지.
    - 값이 커지면: 정렬 대상이 크거나, 정렬 버퍼가 부족해서 “여러 번 나눠 정렬”했을 가능성.
- Sort_range
    - **인덱스 레인지 스캔 결과**를 대상으로 정렬이 발생한 횟수.
    - 즉, 인덱스로 범위를 좁혀 읽긴 했지만, 결과 정렬은 별도로 했다는 신호일 수 있음.
- Sort_scan
    - **풀스캔 결과**를 대상으로 정렬이 발생한 횟수.
    - 값이 늘면: 조건이 약해서 테이블을 많이 읽고 정렬까지 하고 있을 가능성.
- Sort_rows
    - 정렬한 전체 레코드 수.
    - “정렬 대상이 큰가?”를 체감하기에 좋은 지표.

## **포인트**

- “정렬이 문제 같다” 싶으면:
    - EXPLAIN에서 Using filesort가 있는지 확인하고,
    - 정렬 관련 상태 변수들이 비정상적으로 튀는지 같이 보면 감이 더 잘 옴.
- 특히 Sort_merge_passes가 증가하면 “정렬이 꽤 무겁게 돌고 있다”는 힌트가 되기 쉬움.

# **4) GROUP BY 처리 방식 3가지**

GROUP BY는 본질적으로 “같은 그룹끼리 모아야” 하니까, 스트리밍을 깨고 **버퍼링 처리가 발생하기 쉬운 대표적인 요소**야.

다만 인덱스 구조에 따라 “모으는 비용”을 크게 줄일 수 있고, 그래서 처리 방식이 나뉜다고 보면 된다.

---

## **(1) 타이트 인덱스 스캔(Tight Index Scan) 기반 GROUP BY**

### **특징**

- GROUP BY 컬럼이 인덱스 순서와 잘 맞으면,
- MySQL은 **인덱스를 앞에서부터 쭉 읽으면서 “그룹이 바뀌는 지점”을 기준으로 자연스럽게 묶을 수 있음**.

### **장점**

- 이미 인덱스가 정렬된 상태이기 때문에,
    - 별도 정렬 작업이 줄거나 없어질 수 있고,
    - 경우에 따라 임시테이블 없이 처리 가능해짐.
- 결과적으로 GROUP BY인데도 상대적으로 가볍게 끝나는 케이스가 생김.

### **언제 기대할 수 있나!**

- GROUP BY a가 있고,
- a가 선두(또는 적절한 순서)의 인덱스로 잡혀 있을 때
- 혹은 쿼리 형태가 인덱스 순서를 깨지 않을 때

---

## **(2) 루스 인덱스 스캔(Loose Index Scan) —**

## **Using index for group-by**

### 특징

- 타이트 스캔이 “쭉 읽으면서 묶는다”라면,
- 루스 스캔은 **“그룹 대표값만 골라서 건너뛰며 읽는”** 느낌이야.
- 예를 들어 그룹이 10만 개면, 모든 레코드를 다 읽는 대신 “그룹이 바뀌는 핵심 지점”만 타고 넘어가면서 그룹을 구성하려고 해.

### **장점**

- 조건이 맞으면 굉장히 빠를 수 있음.
- EXPLAIN의 Extra에 Using index for group-by가 뜨는 식으로 힌트를 주는 경우가 있음.

### **제한/주의**

- 모든 GROUP BY에서 되는 게 아니라 **가능한 형태가 꽤 제한적**이야.
- 인덱스 구성, 쿼리 형태, 집계 함수 종류 등에 따라 “되고/안 되고”가 갈리는 편이라,
    - “루스 스캔이 될 거라 기대”하기보단
    - **EXPLAIN으로 실제 계획을 확인하는 방식**이 안전.

---

## **(3) 임시 테이블(Temporary Table) 기반 GROUP BY**

### **언제 발생하나?**

- 인덱스로 그룹핑을 깔끔하게 처리하기 어려우면,
- MySQL은 내부적으로 **임시 테이블을 만들고** 그 안에서 그룹을 구성해.

### **내부 동작 순서**

- (1) 원본 테이블에서 조건에 맞는 데이터를 읽어옴
- (2) 임시 테이블에 GROUP BY 키를 기준으로 넣고(중복이면 합치고), 집계값을 업데이트
- (3) 임시 테이블이 완성되면 최종 결과를 반환

### **단점**

- 임시 테이블은 크기가 커질 수 있고,
- 커지면 메모리/디스크 부담이 생기면서 성능이 떨어질 수 있어.
- EXPLAIN에서 Using temporary 같은 표시가 보이는 경우가 있어(항상은 아니지만).

---

# **내 쿼리에 적용할 체크리스트**

- EXPLAIN에서 Using temporary / Using filesort가 붙는지 확인
- GROUP BY 컬럼이 **인덱스 선두**에 있는지 확인
- ORDER BY가 GROUP BY/인덱스 순서를 깨는지 확인
- LIMIT이 있는데도 느리다면 “버퍼링 작업(정렬/그룹핑)”이 강제되는 구조인지 의심
- 정렬이 의심되면 Sort_* 상태 변수로 “정렬 빈도/규모” 힌트 확인
